**3\. DB, 스프링 컨텍스트, 네트워크와 함께 검증할 객체를 호출하는 테스트**

DB에 쿼리를 보내는 코드, 스프링이 값을 주입해 줘야 동작하는 코드, 네트워크로 요청을 보내는 코드는 테스트할 객체만 만들어서는 검증할 수 없습니다. 이 절의 테스트도 2절처럼 테스트 코드가 검증할 객체의 메서드를 호출합니다. DB 쿼리를 검증할 때는 DB를, 스프링의 값 주입을 검증할 때는 애플리케이션 컨텍스트를, 통신을 검증할 때는 요청을 받을 서버를 준비합니다.

**기법 5. DB 연동은 작은 컨텍스트와 롤백으로 검증합니다.** 책의 예제는 데이터 소스와 트랜잭션 관리자 두 개만 등록한 TestDbConfig 클래스를 만듭니다. DB를 쓰는 여러 테스트가 @SpringJUnitConfig(TestDbConfig.class)로 이 구성을 함께 참조합니다. 같은 테스트 프로세스에서 스프링이 캐시에 보관한 동일한 컨텍스트를 재사용하는 동안에는 그 안의 내장 DB와 스키마도 함께 재사용됩니다. 테스트에 @Transactional을 붙이면 테스트가 끝날 때 트랜잭션이 롤백(작업을 취소하고 이전 상태로 되돌림)됩니다. 다음 테스트를 실행할 때 이전에 넣은 데이터가 남아 있지 않아서 같은 조건으로 반복적인 테스트가 가능해집니다.

다음은 DB의 데이터를 페이지 단위로 나눠 읽는 JdbcPagingItemReader로 사용자별 접속 건수를 읽는 기능의 테스트입니다. @Sql로 테스트 데이터를 넣고 리더를 호출해 읽은 결과를 검증합니다.

이 테스트는 페이지 크기를 2로 지정했습니다. 조회 결과가 두 건이므로 세 번째 read()는 두 번째 페이지를 조회합니다. 그 페이지가 비어 있어 반환값은 null입니다. 이 쿼리는 사용자 이름으로 집계하고 그 이름순으로 정렬하므로 한 사용자의 접속 기록을 여러 건 넣어도 조회 결과는 한 행입니다. 두 번째 페이지의 데이터까지 검증하려면 서로 다른 사용자 세 명의 기록을 넣습니다. 페이지 크기가 2일 때 세 번째 사용자까지 이름순으로 읽고 네 번째 호출에서 null을 반환하는지 확인합니다.

**기법 6. 응답이 정해진 서버에 원격 호출을 실제로 보내 검증합니다.** 실제 원격 호출에서 나오는 응답과 예외 가운데에는 가짜 객체로 충분히 재현할 수 없는 것도 있습니다. 그렇다고 운영 환경의 서버를 호출하기에는 부작용이 크고 개발 환경의 서버로도 원하는 응답을 재현하는 데 노력이 많이 들어가는 경우가 있습니다. 그래서 통신은 SMTP(메일 전송 프로토콜)나 HTTP 같은 실제 프로토콜로 하되, 호출 대상을 테스트 코드가 직접 실행한 서버나 응답을 미리 아는 서버로 지정하는 기법이 필요합니다.

메일 전송을 예로 들어 보겠습니다. 기법 2를 따른다면 '잡이 성공하면 메일을 보내지 않는다'는 조건을 Mockito와 같은 가짜 객체 생성 라이브러리로 검증할 수 있습니다. 메일을 보내는 경우도 Mockito로 전송 메서드에 넘어온 인자를 확인할 수는 있습니다. 하지만 그 메일이 SMTP로 전송되는지, 인코딩된 제목이 서버가 받은 뒤에도 원래 문자열인지는 가짜 객체로 확인할 수 없습니다.

메일을 보내는 리스너의 테스트는 GreenMail(테스트 코드 안에서 메일 서버를 실행해 주는 라이브러리)로 로컬 메일 서버를 실행합니다. 리스너는 운영 환경에서와 똑같이 SMTP로 이 서버에 메일을 보냅니다. 테스트는 서버가 받은 메일이 한 통인지, 제목과 수신자가 기대한 값과 같은지를 쉽게 검증합니다.

책의 URL 검사 예제는 공개 사이트 한 곳의 주소 두 개에 요청을 보내 각각 200과 404를 기대합니다. 두 값은 모두 HTTP 응답의 상태 코드입니다. 스킴(https://처럼 주소 앞에서 통신 방식을 나타내는 부분)이 빠진 주소를 넘기는 테스트에서는 요청을 만들 때 IllegalArgumentException이 발생하는지 확인합니다.

시간 제한은 URL을 호출하는 클래스가 생성자로 받아 HttpRequest.Builder.timeout()에 전달합니다. 책의 테스트는 요청 제한 시간을 1밀리초로 줄이고 HttpConnectTimeoutException을 기대합니다. 이 예외는 연결을 맺는 도중에 시간이 만료될 때 발생합니다. 연결을 마친 뒤 응답을 기다리다가 시간이 만료되면 HttpTimeoutException이 발생할 수 있습니다. 제한 시간을 1밀리초 같은 극단적인 값으로 바꿔 볼 수 있는 것은 URL을 호출하는 클래스가 제한 시간을 생성자로 받기 때문입니다. 반복 실행할 테스트에서는 앞의 메일 예제처럼 로컬 서버를 띄워 404 응답을 보내거나, 연결을 받은 뒤 응답을 늦춰 요청 타임아웃(정해진 시간 안에 응답이 오지 않음)을 재현할 수 있습니다. 그러면 공개 서버의 상태가 달라져도 같은 조건에서 실패 처리 로직을 점검할 수 있습니다.

**기법 7. 스텝 범위의 빈에 잡 파라미터가 주입되는지 검증합니다.** 이번에는 spring-batch-test 모듈의 StepScopeTestUtils를 활용합니다. 스프링 배치에서는 #{jobParameters\['date'\]} 같은 표현식으로 잡 파라미터의 값을 빈(애플리케이션 컨텍스트가 만들고 관리하는 객체)에 주입합니다. 책의 예제에서 날짜별 파일을 읽는 리더는 스텝 범위(@StepScope)의 빈이므로 스텝 실행 시점에 날짜 값을 주입받습니다. 잡 범위(@JobScope)의 빈도 잡 파라미터를 참조할 수 있습니다. 리더만 호출하는 테스트에서는 날짜를 담은 스텝 실행 정보를 준비합니다.

StepScopeTestUtils.doInStepScope()는 테스트가 만든 StepExecution으로 스텝이 실행 중인 것과 같은 상태를 만들어 줍니다. 다음 테스트는 애플리케이션 컨텍스트 전체를 올리고, 잡 파라미터로 넘긴 날짜의 파일을 리더가 읽는지 검증합니다.

**4\. 스프링 배치로 스텝과 잡을 실행하는 테스트**

여기서부터는 테스트 코드가 스텝이나 잡의 실행을 요청하고, 검증할 객체의 메서드는 스프링 배치가 호출합니다. 책의 예제는 애플리케이션 컨텍스트에 등록된 스텝이나 잡을 실행합니다. 업무 코드가 DB를 사용하거나 JDBC 잡 저장소로 실행 이력과 재시작을 검증할 때는 DB도 준비합니다. 기법 8은 레퍼런스 매뉴얼에 예제 코드가 있으므로 여기서는 코드를 싣지 않고 쓰임새와 주의할 점만 적습니다. 기법 9는 1절에서 본 CheckUrlJobTest를 예로 설명합니다.

**기법 8. 스텝 하나만 실행합니다.** JobOperatorTestUtils.startStep()은 잡에 속한 스텝 가운데 하나만 실행합니다. 잡 전체를 종단간으로 테스트하기 어려울 때 테스트하기 쉬운 스텝만 골라 실행할 수 있습니다. 에러가 나는 스텝만 반복해서 디버깅할 때도 유용합니다. 기법 4처럼 태스클릿을 직접 호출하는 테스트와 달리 스텝을 구성하는 코드와 잡 파라미터의 주입까지 함께 검증됩니다.

1절 '잡의 종단간 테스트만 할 때의 한계'에서 예로 든 URL 리스너는 책에서 앞 글의 세 에이전트(코덱스 gpt-5.6-sol, 클로드 코드 페이블 5·오퍼스 5)에게 같은 요청문으로 한 번씩 맡긴 사례입니다. 세 에이전트 모두 리스너를 스텝에 등록했지만 새로 작성한 테스트는 리스너 메서드를 직접 호출했습니다. 그 테스트는 스텝을 구성하는 코드에서 리스너 등록이 빠져도 통과합니다. 이 등록을 검증하려면 startStep()으로 URL 검사 스텝만 실행해도 됩니다. 1절에서 본 것처럼 응답을 3초 넘게 늦추는 서버를 쓸 때는 요청이 먼저 만료되지 않게 준비해야 합니다. 책에서는 기록 기준을 1밀리초로 낮춘 뒤 잡을 실행해 URL이 기록되는지 확인했습니다. 어느 방법이든 기록 기준을 넘는 응답이 나오게 하고 출력 파일에 그 URL이 기록됐는지 확인하면 스텝을 구성하는 코드에서 리스너 등록을 빠뜨렸을 때 테스트가 실패합니다.

**기법 9. 잡을 처음부터 끝까지 실행합니다.** 1절의 CheckUrlJobTest처럼 테스트 클래스에 @SpringBatchTest를 붙이면 JobOperatorTestUtils가 컨텍스트에 등록됩니다. 테스트는 이 객체를 주입받아 startJob() 메서드로 잡을 실행하고 실행 결과인 JobExecution을 받습니다.

책의 일별 백업 잡을 예로 들어 보겠습니다. 이 잡은 처음 용량을 검사했을 때 공간이 부족하면 오래된 백업을 지우고 용량을 다시 검사합니다. 각 스텝이 단독으로 성공해도 잡 구성에서 다음 스텝을 잘못 연결할 수 있습니다. 이 분기를 타는 조건으로 잡을 실행하고 삭제 스텝과 재검사가 차례로 수행됐는지 확인하면 그런 연결 오류를 찾을 수 있습니다.

종단간 테스트를 작성할 때는 스프링 부트와 스프링 배치의 기본 동작 때문에 테스트에서 따로 설정할 것이 네 가지 있습니다.

• 스프링 부트는 컨텍스트가 뜰 때 잡을 자동으로 실행합니다. 테스트에서는 spring.batch.job.enabled=false 속성으로 이 기능을 끕니다. 1절의 테스트는 @SpringBootTest에 이 속성을 지정했습니다.

• 잡 이름과 식별 잡 파라미터가 같으면 같은 잡 인스턴스입니다. 실행 이력을 보존하는 저장소에서는 완료된 인스턴스를 다시 시작하면 예외가 납니다. 서로 독립적인 테스트에서는 getUniqueJobParametersBuilder()로 고유한 식별 값을 추가해 매번 새 인스턴스를 실행합니다. 1절의 테스트도 이 메서드로 잡 파라미터를 만듭니다.

• 기본 설정의 JDBC 잡 저장소는 잡 인스턴스나 실행을 만들 때 이미 활성 트랜잭션이 있으면 예외를 던집니다. 이 저장소로 잡을 실행하는 테스트에는 @Transactional을 붙이지 않습니다. 책의 프로젝트 규칙은 이 에러를 없애려고 spring.batch.jdbc.validate-transaction-state 속성을 끄는 것도 금지합니다.

• 실행 이력을 DB에 남길 필요가 없는 테스트에는 ResourcelessJobRepository를 테스트용 빈으로 등록해 실행 이력 테이블 없이 잡을 실행합니다. 다만 이 구현체는 잡을 병렬로 실행하거나 재시작하는 테스트에는 쓸 수 없습니다.

잡의 실행 상태만 단언해서는 부족합니다. 상태가 COMPLETED인지만 확인하는 테스트는 아무 데이터도 남기지 않는 잡도 통과시킵니다. 책의 4장 예제는 결과 테이블에 행이 들어갔는지와 출력 파일에 한 줄 이상 기록됐는지까지 단언합니다. 출력 파일이 존재하는지만 검사하면 0바이트 파일도 통과하기 때문입니다. 그리고 이전 실행이 남긴 파일 덕분에 테스트가 통과하는 경우가 없도록 잡을 실행하기 전에 출력 파일을 지웁니다.

**기법 10. 빈 입력과 실패·중단 상황에서 잡의 동작을 검증합니다.** 예외 상황에서 무엇을 확인할지는 잡의 요구 사항에 따라 달라집니다. 입력이 비었을 때 어떤 상태로 끝나는지와 중단한 작업을 어디서 이어 가는지는 서로 다른 테스트 시나리오입니다.

책의 URL 검사 잡에는 스텝이 끝날 때 호출되어 읽은 아이템이 하나도 없으면 스텝의 종료 상태를 'FAILED'로 바꾸는 리스너 메서드가 있습니다. 다음 테스트는 내용이 없는 파일을 입력으로 잡을 실행합니다.

이 테스트는 두 가지 상태를 단언합니다. 리스너가 바꾸는 값은 종료 상태(ExitStatus)뿐이고 실행 상태(BatchStatus)는 COMPLETED가 됩니다. 이 테스트가 확인하는 대상은 잡 실행 결과인 JobExecution입니다. 책의 명령행 애플리케이션은 스프링 부트가 잡의 실행 상태로 정한 종료 코드를 운영체제에 전달하므로, 이 예제처럼 실행 상태가 COMPLETED이면 스케줄러에 전달되는 값은 0입니다.

실패·중단 처리는 다음과 같이 별도로 검증합니다.

• 실행 이력을 보존하도록 구성하고 재시작 가능한 잡을 실패시킨 뒤, 같은 식별 파라미터로 다시 실행했을 때 의도한 곳부터 처리를 이어 가는가. 두 번째 실행에서 기법 9처럼 새 식별 값을 만들면 새 인스턴스가 시작되어 재시작 동작을 검증할 수 없습니다.

• 실행 중인 잡에 중단 신호를 보내면 잡이 멈추고, 멈춘 잡을 다시 시작할 수 있는가.

• 스텝에 선언한 재시도 정책이 의도대로 동작하는가.

**종단간 테스트를 실행하기 어려운 잡에서는 기법을 조합합니다.** 1절 '잡의 종단간 테스트만 할 때의 한계'에서 든 네 가지 상황에 해당하는 잡에는 기법 9의 종단간 테스트를 그대로 쓰기 어렵습니다. 잡의 실행 시간이 길다면 종단간 테스트를 만들되 코드를 고칠 때마다 실행하지 않고 실행 시점을 조정합니다. 그 방법은 5절에서 설명합니다. 테이블 잠금 때문에 다른 테스트가 실패하는 잡, 초기 데이터를 준비하기 어려운 잡, 실행 전의 상태로 되돌리는 비용이 큰 잡에는 종단간 테스트를 고집하지 않고 앞에서 소개한 기법을 대신 씁니다. 파일 해석이나 업무 규칙 같은 로직은 기법 1~7로 나눠서 검증하고, 스텝을 구성하는 코드는 기법 8로 테스트하기 쉬운 스텝만 실행해서 확인합니다. 운영 서버에 배포하기 전에 개발 서버에서 잡 전체를 실행해 에러가 없는지 확인하는 절차는 거쳐야 합니다.

> 직접 호출하는 테스트에서는 경계값을 바꿔 업무 규칙을 확인합니다. 스텝이나 잡을 실행하는 테스트에서는 해당 경로를 타는 입력을 주고 출력이나 실행 이력을 확인해 구성 요소 사이의 연결을 검증합니다. 자동화된 종단간 테스트를 실행하기 어려운 잡이라도 배포하기 전에 잡을 실행해 보는 확인까지 생략할 수는 없습니다.

**5\. 테스트 종류의 명칭을 팀 안에서 통일하고 실행 시점을 나눕니다**

10가지 기법은 테스트를 실행하는 범위와 실행에 드는 비용에서 차이가 있습니다. 2절의 테스트는 객체를 직접 만들고 DB나 네트워크에 연결하지 않아서 빨리 끝납니다. 잡 전체를 실행하는 테스트는 잡에 필요한 입력을 준비하고 실행이 끝날 때까지 기다려야 합니다. 코드를 고칠 때마다 모든 테스트를 실행한다면 효율성이 떨어지므로 테스트의 범위에 따라 실행 시점을 나눠야 합니다. 그렇게 테스트를 구분하려면 테스트의 종류를 가리키는 명칭도 통일해야 합니다. 그렇지 않으면 사람 사이에 소통하거나 AI 에이전트에게 지시할 때 혼란이 생기고, 빌드 설정에서 특정 시점에 실행할 테스트를 묶어 지정하기도 어렵습니다.

**'단위 테스트'가 가리키는 범위도 문서마다 다릅니다.** 스프링 배치 매뉴얼이 단위 테스트라고 부르는 범위는 스프링 프레임워크 매뉴얼과 다릅니다. 두 레퍼런스 매뉴얼을 나란히 놓으면 다음과 같습니다.

•: 첫 절부터 잡의 애플리케이션 컨텍스트를 올려서 잡을 실행하는 테스트를 단위 테스트(unit test)라고 부릅니다. 장 서문에서는 스프링으로 하는 단위 테스트와 통합 테스트는 스프링 프레임워크 문서에 자세히 나와 있으므로 반복하지 않고, 이 장은 배치 잡의 종단간 테스트를 다룬다고 밝힙니다.

• 과: 스프링이나 다른 컨테이너 없이 new로 만든 객체를 검증하는 테스트를 단위 테스트로 설명하고, 애플리케이션 컨텍스트를 올리는 테스트는 통합 테스트로 따로 다룹니다.

이 책의 저자는 두 매뉴얼의 이런 차이를 스프링 배치 프로젝트에 로 알리고, 장 제목을 'Unit Testing'에서 'Testing'으로 바꾸는 을 올렸습니다. 이 글을 쓰는 시점에는 아직 병합되지 않아서 매뉴얼의 장 제목은 'Unit Testing' 그대로입니다.

이 글에서는 2절처럼 스프링 컨텍스트, DB, 네트워크 연결 없이 객체를 직접 호출해 동작을 검증하는 테스트를 단위 테스트라고 부릅니다. 기법 6의 URL 검사 테스트는 URL 호출이 그 클래스의 기능이고 객체를 직접 만들어 호출하므로 단위 테스트로 볼 수도 있습니다. 하지만 실제 서버와 HTTP로 통신하므로 네트워크 연결이 없어야 단위 테스트라고 보는 기준에서는 단위 테스트가 아닙니다. 같은 용어가 다르게 쓰이므로 '단위 테스트를 추가해 주세요'라는 리뷰 의견도 사람마다 다르게 받아들일 수 있습니다. AI 에이전트에게 '단위 테스트를 작성하라'고만 지시하면 에이전트가 어느 범위로 해석할지 알 수 없습니다. 요청문이나 지침 파일(AGENTS.md처럼 에이전트가 세션마다 읽는 프로젝트 규칙 파일)에 애플리케이션 컨텍스트를 올릴지, 어떤 종류의 객체를 가짜로 바꿀지처럼 테스트의 범위를 명시해야 의도한 범위의 테스트가 작성됩니다.

**테스트의 종류를 '단위'와 '통합' 두 가지로만 나누지 않아도 됩니다.** 이 글의 절 제목처럼 DB나 컨텍스트나 네트워크 없이 검증할 객체를 호출하는 테스트, 그것들과 함께 호출하는 테스트, 스텝을 실행하는 테스트, 잡 전체를 실행하는 테스트로 기법에 따라 나눌 수 있습니다. 둘째 종류 안에서도 DB가 필요한 테스트와 외부 주소를 호출하는 테스트는 준비할 환경과 실행 비용이 다르므로 더 세밀하게 나눌 수도 있습니다. 분류한 종류에는 팀이 함께 쓸 명칭을 정하고, 코드에서도 그 구분이 드러나게 합니다. 방법은 두 가지입니다.

• **클래스 이름**: 테스트 종류마다 클래스 이름의 접미사를 정해 둡니다. 메이븐(Maven)에서 테스트를 실행하는 Surefire 플러그인은 기본 설정으로 이름이 Test로 끝나는 클래스 등을 실행합니다. 통합 테스트용 Failsafe 플러그인을 추가하면 이름이 IT로 끝나는 클래스 등을 따로 실행합니다.

• **JUnit 태그**: 잡 전체를 실행하는 테스트 클래스에 @Tag("job")처럼 태그를 붙입니다. 그레이들에서는 테스트 태스크의 useJUnitPlatform() 블록에 includeTags와 excludeTags를 지정해서 실행할 태그를 고릅니다. 클래스 이름을 바꾸지 않고도 종류를 나눌 수 있고, 한 테스트에 태그를 여러 개 붙일 수도 있습니다.

**실행 시점은 테스트의 실행 비용에 따라 나눕니다.** 실행 비용에는 실행 시간과 함께 DB, 입력 파일, 외부 시스템처럼 테스트에 필요한 환경을 준비하는 수고도 들어갑니다. 종류를 구분해 두면 다음과 같이 시점마다 실행할 테스트를 지정할 수 있습니다.

• **로컬 개발 환경**: 코드를 고칠 때마다 2절의 테스트처럼 금방 끝나는 테스트를 실행합니다. AI 에이전트가 작업하는 동안 받는 피드백도 주로 이 테스트에서 나옵니다. 책의 2장은 전체 테스트에 몇 분씩 걸리는 프로젝트라면 에이전트의 훅(hook, 에이전트 도구가 정해진 시점에 자동으로 실행하는 스크립트)이 전체 테스트를 실행하는 시점을 작업을 마칠 때에서 커밋이나 푸시 직전으로 옮기는 방법을 설명합니다.

• **PR을 병합하기 전**: CI 서버에서 DB, 컨텍스트, 네트워크와 함께 검증할 객체를 호출하는 3절의 테스트와 스텝, 잡을 실행하는 4절의 테스트를 실행합니다. 각자의 브랜치에서는 통과하던 코드도 브랜치를 합치면 서로 충돌해 실패할 수 있으므로 합쳐질 소스를 검증하는 일은 CI가 맡습니다.

• **서버에 배포하기 전**: 운영 환경과 비슷한 양의 데이터로 잡을 실행하는 테스트, 배포할 jar 파일을 직접 실행해 보는 확인처럼 오래 걸리거나 준비할 환경이 많은 검증을 실행합니다. 4절 끝에서 말한 '개발 서버에서 잡 전체를 실행해 에러가 없는지 확인하는 절차'도 이 시점에 거칩니다.

4절 끝에서 실행 시간이 긴 잡은 종단간 테스트의 실행 시점을 조정한다고 했습니다. 이런 테스트에 태그를 붙여 로컬 빌드에서 빼고 배포 전에 실행하도록 지정하면 느리다는 이유로 테스트를 포기하지 않아도 됩니다.

**6\. 테스트하기 쉬운 구조는 잡을 설계할 때 정해집니다**

2절과 3절의 기법은 대부분 코드가 그 기법에 맞는 구조를 갖춰야 쓸 수 있습니다. 각 기법에서 설명한 전제 조건을 모으면 다음과 같습니다.

• 파일 해석, 기록처럼 따로 검증할 로직은 클래스를 분리합니다(기법 1).

• 의존하는 객체와 제한 시간, 경로, 보관 기간 같은 값은 생성자로 받습니다(기법 2, 3, 6).

• 시각, 알림 전송, 원격 호출처럼 테스트에서 통제하기 어려운 대상은 NotificationService처럼 인터페이스를 정의하거나 Clock처럼 JDK에 이미 있는 타입으로 받습니다(기법 2, 3).

잡을 완성한 후에 이 구조로 바꾸려면 클래스와 메서드를 분리하고 의존 관계를 다시 연결해야 합니다. 이미 작성한 코드를 바꿔야 하므로 AI 에이전트의 작업 횟수와 토큰 비용도 늘어납니다. 그래서 어떤 기능을 어떤 기법으로 테스트할지는 잡의 기능 명세를 작성할 때 함께 설계해야 합니다. 그래야 적은 시행착오로 완성도 높은 배치 잡을 만들 수 있습니다. 책의 1장에서는 다음과 같이 설명합니다.

> '이 프로그램은 배치 프로그램이라서 테스트 코드 작성이 아예 힘들다'라는 말이 나온다면 그것은 해결해야 할 구조적인 문제가 있다는 신호다.

AI 에이전트에게 잡 개발을 맡길 때 앞의 세 가지 구조를 직접 지시하면 정밀한 테스트가 작성될 가능성이 높아집니다. 앞 글에서 본 것처럼 요청문에 명시하지 않은 부분은 에이전트마다 다르게 구현되고, 같은 에이전트라도 매번 같은 결과가 나온다는 보장이 없습니다.

책의 예제 프로젝트는 구조와 테스트 방식을 지침 파일인 AGENTS.md에 명시합니다. 앞의 셋째 조건은 이 파일에 다음과 같이 적혀 있습니다.

• 파일 시스템·시각·원격 호출처럼 테스트에서 통제하기 어려운 대상은 인터페이스로 추상화하고 생성자로 주입받는다.

2절 첫머리에서 인용한 '가능하면 애플리케이션 컨텍스트를 올리지 않고 객체를 직접 생성해 단위 테스트한다'도 이 파일에 적힌 규칙입니다.

**핵심 정리**

**• 잡의 종단간 테스트는 스텝 사이의 흐름을 검증할 수 있습니다. 다만 잡 전체를 실행하기 어려운 경우가 있고, 실패했을 때 원인을 찾을 범위도 넓습니다.**

**• DB, 스프링 컨텍스트, 네트워크 없이 검증할 객체를 호출하는 테스트(기법 1~4), 그것들과 함께 호출하는 테스트(기법 5~7), 스프링 배치로 스텝과 잡을 실행하는 테스트(기법 8~10)를 찾으려는 오류에 따라 선택하고 조합합니다.**

**• 직접 호출하는 테스트는 경계값을 바꿔 업무 규칙을 검증하고, 스텝이나 잡을 실행하는 테스트는 그 경로를 타는 입력으로 구성 요소 사이의 연결을 검증합니다. 리스너를 스텝에 등록하는 코드가 빠져도 리스너를 직접 호출하는 테스트는 통과하므로 두 종류가 모두 필요합니다.**

**• 테스트의 범위와 기법에 따라 테스트의 종류를 나눠 명명하고, 클래스 이름이나 JUnit 태그로 구분해서 로컬, PR 병합 전, 배포 전처럼 실행 비용에 맞는 시점에 실행합니다.**

**• 상당수 기법은 코드가 생성자 주입이나 인터페이스 추상화 같은 구조를 갖춰야 쓸 수 있습니다. 그래서 잡의 기능과 테스트 방식은 함께 설계하고, 그 구조를 AI 에이전트에게 요청문이나 지침 파일로 지시합니다.**

**마무리: 다음 단계는?**

이 글에서는 파일 한 줄을 해석하는 규칙부터 스텝 사이의 연결과 실패·중단 처리까지, 찾으려는 오류에 따라 테스트를 구성하는 방법을 살펴봤습니다. 기법마다 전체 코드와 테스트가 실패했을 때 원인을 찾아가는 과정은 책의 각 장에서 예제와 함께 다룹니다.

테스트로 철저히 검증해도 운영 환경에서는 개발 환경과 다른 양의 데이터와 외부 시스템의 응답을 만납니다. 그때 생기는 문제를 발생 직후에 확인하고 대응하려면 잡의 실행 상태와 처리 건수, 실행 시간을 모니터링하고 잡이 실패하면 경보를 받는 구성이 필요합니다. 책의 15장 '잡 실행 모니터링'에서 메타데이터 테이블 조회, 액추에이터와 프로메테우스·그라파나를 이용한 메트릭 수집, 잡 실패 경보를 자세히 다룹니다.

**이 글에서 소개하지 않은 기법** 책에는 이 글에서 다루지 않은 테스트 기법이 더 있습니다.

• 여러 개의 입력값과 기대 결과의 조합을 하나의 테스트 메서드로 검증하는 방법. 책에서는 날짜에 따라 다음에 실행할 스텝을 정하는 판단을 JobExecutionDecider 구현체로 분리하고, JUnit의 @ParameterizedTest로 경계 날짜를 넣어 모든 분기 경로를 검증합니다. 기법 4에서 본 백업 판단 테스트와 실행 시간을 '시:분:초' 문자열로 바꾸는 메서드도 같은 방법으로 여러 조합을 검증합니다.

• 코드에 지정한 크론 표현식(실행 일정을 적는 문자열)으로 다음 실행 시각을 계산해 기대한 시각 목록과 비교하는 방법

• MockMvc(서버를 띄우지 않고 컨트롤러에 요청을 보내는 스프링의 테스트 도구)로 오래 걸리는 잡의 시작을 요청하고 HTTP 200 응답을 확인하는 방법
