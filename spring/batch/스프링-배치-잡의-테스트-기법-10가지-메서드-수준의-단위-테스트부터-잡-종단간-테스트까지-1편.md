**잡 전체를 실행하는 테스트 하나로 배치 잡의 오류를 다 찾을 수 있을까?**

근래의 AI 모델은 코드를 고친 뒤 컴파일과 테스트 실행 같은 검증까지도 알아서 잘합니다. 하지만 LLM은 불확정적으로 동작하기에 항상 충분한 검증을 한다고 보장할 수는 없습니다.

앤트로픽(Anthropic)의 연구자 니컬러스 칼리니(Nicholas Carlini)는 클로드 에이전트 16개를 병렬로 실행해서 러스트로 C 컴파일러를 처음부터 만들었습니다. 약 2,000번의 클로드 코드 세션 끝에 리눅스 6.9 커널을 빌드할 수 있는 10만 줄 규모의 컴파일러가 나왔습니다. 그는 에서 노력의 대부분을 클로드가 혼자서도 방향을 잡도록 테스트와 피드백 같은 환경을 설계하는 데 들였다고 밝힙니다. 그리고 교훈의 첫 항목으로 '품질이 아주 높은 테스트를 작성하라'를 꼽으며 다음과 같이 설명합니다.

> 클로드는 내가 준 문제가 무엇이든 자율적으로 해결하려 한다. 그래서 작업을 검증하는 장치가 거의 완벽한 것이 중요하다. 그렇지 않으면 클로드는 엉뚱한 문제를 해결하게 된다.

테스트가 확인하지 않는 동작이 있으면 에이전트는 그 동작의 오류를 남긴 채 작업을 마칠 수 있습니다. 반대로 테스트할 기능의 범위와 시나리오를 상세하게 지시하면 에이전트는 실패한 테스트를 보고 오류를 고치면서 완성도 높은 코드를 작성할 가능성이 높아집니다. 이 연재의 첫 글에서 본 것처럼 배치 잡은 개발 환경에서 성공한 실행이 운영 환경의 성공을 보장하지 못합니다. 그래서 업무 로직을 분기시키는 경계값과 코너 케이스를 테스트 코드로 따로 검증해야 합니다.

이런 테스트를 어떻게 작성할지는 보통 프레임워크의 공식 문서에서 먼저 찾아봅니다. 자바로 배치 잡을 만들 때 대표적으로 쓰는 프레임워크는 스프링 배치입니다. 책의 기준 버전인 스프링 배치 6.0.6의 레퍼런스 매뉴얼은 16개 장 가운데 13번째인 'Unit Testing' 장에서 테스트를 다룹니다. 매뉴얼을 순서대로 읽으면 테스트는 한참 뒤에야 나옵니다. 해당 장은 테스트 클래스 구성을 설명한 뒤 곧바로 잡의 종단간 테스트를 소개합니다. 그렇다면 파일 해석이나 업무 규칙에서 생기는 오류까지 잡 전체를 실행해서 찾아야 할까요?

《AI 에이전트와 스프링 배치를 활용한 배치 엔지니어링》은 2장부터 테스트 코드를 예제로 설명하고, 장마다 다른 테스트 기법을 소개합니다. 책에 포함된 자바 코드의 3분의 1인 약 1,900줄이 테스트 코드입니다. 책에서 일부를 생략한 코드까지 모두 담은 예제 프로젝트에서는 자바 코드 약 9,400줄 가운데 약 3,900줄(41%)이 테스트 코드입니다.

이 글에서는 책에 나온 테스트 기법 10가지를 정리합니다. 기법은 검증할 객체의 메서드를 누가 호출하느냐에 따라 구분했습니다. 기법 1~7에서는 테스트 코드가 검증할 객체의 메서드를 직접 호출합니다. 기법 1~4는 DB, 스프링 컨텍스트, 네트워크 없이 실행하고, 기법 5~7은 검증할 동작에 필요한 환경을 함께 준비합니다. 기법 8~10에서는 스프링 배치가 스텝(잡을 나눈 처리 단계)이나 잡을 실행합니다. 스텝 하나의 구성, 스텝 사이의 연결, 빈 입력과 실패·중단 상황에서의 동작을 차례로 살펴봅니다.

**1\. 잡의 종단간 테스트만 할 때의 한계**

잡의 종단간 테스트는 테스트 코드 안에서 잡을 처음부터 끝까지 실행하고 결과를 확인합니다. 운영 환경에서 실행할 때와 같은 잡 구성과 스텝 순서로 실행하므로 배포 전에 자동이든 수동이든 한 번은 필요한 테스트입니다. 다만 이 기법 하나로만 자동화된 테스트를 구성하기에는 한계가 세 가지 있습니다.

**첫째, 종단간 테스트를 실행하기 어려운 잡이 있습니다.** 책에서는 다음 네 가지 상황을 듭니다.

• 잡의 실행 시간이 테스트 환경에서도 길어서 전체 빌드 시간이 크게 늘어납니다.

• 잡이 실행되는 동안 테이블 잠금 때문에 다른 테스트가 실패할 수 있습니다.

• 잡 실행에 필요한 초기 데이터를 개발 환경에서 준비하기 어렵습니다.

• 반복해서 테스트하려면 DB나 외부 시스템을 잡 실행 전의 상태로 되돌려야 하는데 그런 구성을 하는 비용이 클 때가 있습니다.

**둘째, 테스트가 실패했을 때 원인을 찾을 범위가 넓습니다.** 잡 하나에는 파일 해석, 업무 규칙, DB 쿼리, 스텝 사이의 분기가 모두 들어 있습니다. 처음 실행한 잡에는 여러 오류가 섞여 있을 가능성이 높아서 어느 클래스의 오류인지부터 찾아내야 합니다. 에러가 발생한 클래스는 스택 트레이스로 알 수 있지만, 고쳐야 할 코드는 다른 클래스에 있을 수도 있습니다. 예를 들어 DB에 쓰는 코드에서 예외가 났더라도 파일을 잘못 해석해서 빈 값을 넘긴 클래스가 원인일 수도 있습니다.

**셋째, 예외 상황과 경계값을 재현하려면 준비할 요소가 많습니다.** 형식에 어긋난 데이터, 삭제 기준일과 하루 차이 나는 디렉터리, 세 번 실패하고 네 번째에 성공하는 원격 호출을 떠올려 봅시다. 잡 전체를 실행할 때 이런 조건을 만들려면 입력 파일과 DB, 외부 시스템의 상태를 바꿔야 합니다.

응답이 느린 URL을 파일에 기록하는 리스너(스텝 실행이나 아이템 처리 등의 이벤트에 맞춰 호출되는 객체)를 예로 들어 봅시다. 책의 URL 검사 잡에 추가하는 이 리스너는 응답 시간이 3초를 넘은 URL을 slow-url.txt 파일에 기록합니다. 이 잡의 종단간 테스트는 다음과 같습니다.

이 테스트는 실제로 호출할 주소 두 개를 담은 입력 파일(ok-urls.txt)과 잡 파라미터를 준비합니다. 책에서 이 테스트를 실행했을 때는 두 주소가 모두 3초 안에 응답해서 리스너가 기록한 URL이 없었습니다. 이처럼 모든 URL이 빠르게 응답하면 리스너 등록이 빠진 경우와 올바르게 동작한 경우 모두 파일이 비어 있을 수 있습니다.

리스너가 느린 URL을 기록하는지 확인하려면 응답에 3초 넘게 걸리는 주소를 입력 파일에 넣어야 합니다. 이 잡은 HTTP 요청의 제한 시간도 3초이지만 책의 예제가 쓰는 JDK 25에서는 서버가 응답을 시작할 때까지만 이 제한 시간이 적용됩니다. 반면 느린 URL인지 판단하는 응답 시간은 요청을 보낸 때부터 응답 본문을 다 받을 때까지 걸린 시간입니다. 느린 응답을 재현하려면 3초 안에 응답을 시작하되 본문을 다 보내는 데는 3초 넘게 걸리는 서버를 준비하거나, 테스트에서 요청 제한 시간을 기록 기준보다 길게 늘려야 합니다. 이전 실행이 남긴 기록 파일도 지워야 합니다.

그래서 잡의 종단간 테스트만으로 모든 오류를 찾으려 하지 않고, 찾으려는 오류에 맞춰 테스트를 따로 구성해야 합니다. 앞의 잡을 예로 들면 리스너 등록이 빠지는 오류는 응답에 3초 넘게 걸리는 주소를 입력 파일에 넣고 URL 검사 스텝만 실행해서 찾습니다. 실행이 끝나면 리스너가 느린 URL을 남기는 파일에 그 주소가 기록됐는지 확인합니다. 파일 한 줄을 잘못 해석하는 오류는 잡을 실행하지 않고 한 줄을 해석하는 메서드만 호출한 뒤 반환된 객체의 필드를 확인해서 찾습니다.

**2\. DB, 스프링 컨텍스트, 네트워크 없이 검증할 객체를 호출하는 테스트**

애플리케이션 컨텍스트는 스프링이 객체를 만들고 서로 연결해 보관하는 저장소입니다. 이 절의 테스트는 컨텍스트를 올리지 않고 DB나 네트워크에도 연결하지 않습니다. 그래서 실행 속도가 빠르고, 실패했을 때 살펴볼 코드의 범위도 좁습니다. 책의 예제 프로젝트는 '가능하면 애플리케이션 컨텍스트를 올리지 않고 객체를 직접 생성해 단위 테스트한다'를 프로젝트 규칙으로 명시합니다.

**기법 1. 역할을 세밀하게 나눈 클래스를 테스트합니다.** 예를 들어 CSV 한 줄을 AccessLog 객체로 바꾸는 AccessLogLineMapper는 new로 생성해서 문자열 한 줄을 파싱하고, 반환된 객체의 필드를 단언(assert, 기대한 값과 같은지 확인)합니다.

출처: 《AI 에이전트와 스프링 배치를 활용한 배치 엔지니어링》 108~109쪽

파일을 읽는 코드와 한 줄을 해석하는 코드가 분리되어 있기 때문에 이러한 테스트를 할 수 있습니다. 두 코드가 한 메서드에 섞여 있었다면 특이한 데이터 한 건만 검증하려고 해도 파일을 준비해야 합니다. 앞 글에서 D1로 든 '메서드 하나가 너무 많은 일을 떠안는 코드'가 이런 경우입니다. 스프링 배치의 기본 구성 요소는 역할이 세분화되어 있기에 테스트에도 유리합니다. 파일을 한 줄씩 읽는 스프링 배치의 리더(스텝이 처리할 데이터를 읽어 오는 객체)인 FlatFileItemReader는 한 줄을 객체로 바꾸는 일을 LineMapper에 맡깁니다. 책에서는 앞의 AccessLogLineMapper가 LineMapper를 구현하도록 고쳐 FlatFileItemReader의 속성으로 지정합니다. 파일 전체를 읽는 일은 프레임워크가 맡으므로 직접 만든 클래스의 테스트는 한 줄의 해석만 검증하면 됩니다.

이 기법으로 스프링 배치가 제공하는 구성 요소를 직접 호출하여 프레임워크의 기능을 학습할 수도 있습니다. 예를 들어 ListItemReader라는 클래스에 아이템(처리할 데이터 한 건) 2개를 저장하고 read() 메서드를 세 번 호출해서 세 번째에 null이 반환되는지 확인합니다. 책에서는 이런 테스트를 학습용 테스트라고 부릅니다.

**기법 2. 외부 시스템을 호출하는 코드는 가짜 객체로 바꿔 검증합니다.** 예를 들어 알림 전송을 테스트에서 그대로 실행하면 테스트할 때마다 슬랙 같은 실제 알림 채널로 메시지가 나갑니다. 그 메시지가 도착했는지와 형식이 의도한 대로 나오는지를 테스트 코드에서 확인하려면 노력이 많이 들어갑니다. 원격 호출은 상대 시스템이 실패하는 상황을 원하는 때에 만들기도 어렵습니다. 이런 기능은 인터페이스로 추상화하고, 테스트에서는 그 인터페이스를 구현한 가짜 객체를 주입합니다. 책에서는 알림을 보내는 NotificationService 인터페이스를 정의하고, 마지막으로 받은 메시지를 저장해 두는 구현체를 테스트용으로 만듭니다.

테스트는 알림을 보내는 클래스에 실제 구현체 대신 MockNotificationService를 주입하고, 기능을 실행한 뒤 이 객체에 남은 메시지를 꺼내 내용을 검증합니다. 이 테스트를 작성하려면 알림을 보내는 클래스가 NotificationService를 생성자로 받아야 합니다. 클래스 안에서 new로 직접 만든 구현체는 테스트에서 바꿀 수 없습니다.

**기법 3. 현재 시각을 테스트가 지정한 값으로 고정합니다.** 배치 잡에는 오늘 날짜를 기준으로 동작이 달라지는 코드가 많습니다. 예를 들어 매달 마지막 날에 실행하는 월 마감 처리는 마지막 날이 28일, 29일, 30일, 31일인 달을 모두 확인해야 합니다. 윤년의 2월 29일은 대개 4년에 한 번만 옵니다. 시스템 시계를 그대로 쓰는 코드는 그 날짜가 될 때까지 기다리지 않으면 이런 경우를 실행해 볼 수 없습니다. 시각을 테스트에서 고정할 수 있으면 원하는 날짜를 넣어 바로 검증합니다.

책에서는 오래된 백업 디렉터리를 지우는 태스크에 이 기법을 씁니다. 수정 시각을 비교하는 부등호가 틀리면 최신 백업이 지워집니다. 게다가 이 태스크는 디스크 용량이 부족할 때만 실행되므로 버그가 있어도 피해가 생긴 뒤에야 발견됩니다.

**기법 4. 잡과 스텝의 실행 정보를 테스트용으로 만들어 구성 요소를 직접 호출합니다.** 스프링 배치는 잡과 스텝을 실행하면서 실행 정보를 담은 JobExecution과 StepExecution을 만들고, 구성 요소의 메서드를 호출할 때 이 객체를 인자로 넘깁니다. 태스클릿(Tasklet, 스텝이 할 일을 직접 구현하는 인터페이스)의 execute(), 스텝 리스너의 afterStep(), JobExecutionDecider(다음에 실행할 스텝을 정하는 스프링 배치의 인터페이스)의 decide()가 그런 메서드입니다. spring-batch-test 모듈의 MetaDataInstanceFactory는 이 객체들을 테스트용으로 만들어 줍니다. 잡 파라미터(잡을 실행할 때 넘기는 입력값)도 함께 넣을 수 있으므로 잡을 실행하지 않고도 이 메서드들을 원하는 조건으로 호출할 수 있습니다.
