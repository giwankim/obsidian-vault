> [!summary]
> Woowa Brothers measured how to cut Redis cost by changing cache value formats: Apache Fory binary serialization instead of Jackson JSON, plus gzip, snappy, or zstd compression. They benchmarked size and speed, then set rules for migrating live caches: dual-write cutover, explicit Fory config and class registration to survive class changes, per-key-group compression flagged by the first byte, and a checklist packaged as an internal AI skill. Rolling out zstd on two production services shrank Redis memory to as little as 31.4% of its previous size (216 GB → 68 GB) and outbound traffic by about half (240 → 116 TB/day).

## 들어가며

백엔드에서 대량 트래픽을 다루다 보면 CPU보다 네트워크와 메모리에서 먼저 병목이 생기는 경우가 많습니다. 캐시는 DB의 부하를 덜어 주지만, 캐시에 담는 값이 커지면 캐시가 오히려 새로운 병목이 됩니다.

같은 값을 초당 수천 번씩 읽는 구조에서는 값 하나를 몇 KB만 줄여도 네트워크 대역폭, 메모리 비용, 직렬화에 드는 CPU가 함께 줄어듭니다. 이 글은 Redis 캐시 값을 어떤 형식으로 저장하고 어떻게 크기를 줄일지 고민한 과정을 정리한 기록입니다.

1장부터 3장까지는 문제와 도구를 소개합니다. 4장에서는 직접 측정한 결과를, 5장과 6장에서는 운영 중인 캐시를 옮길 때의 주의사항과 규칙을 다룹니다.

## 1\. 직렬화 도구와 압축의 필요성

**캐시 값을 줄이면 메모리, 네트워크, CPU 비용이 한꺼번에 줄어듭니다.** 하지만 현재 가장 많이 쓰는 JSON은 읽기 쉬운 대신 크기가 큰 편입니다. JSON은 객체마다 필드 이름을 반복해서 저장하고 숫자도 문자로 표현하기 때문입니다. 아래는 메뉴 두 개를 JSON으로 저장한 예입니다.

```json
[
  {"id": 11, "name": "후라이드치킨", "tags": ["인기"], "stockByShop": {"101": 30}, "createdAt": "2026-11-12T09:12:34.567", "status": "ON"},
  {"id": 12, "name": "양념치킨", "tags": ["인기", "매운맛"], "stockByShop": {"101": 25}, "createdAt": "2026-11-12T09:15:02.118", "status": "ON"}
]
```

메뉴가 수백 개라면 `id`, `name`, `tags`, `stockByShop`, `createdAt`, `status`라는 필드 이름도 수백 번 저장되고, 조회할 때마다 그만큼 네트워크로 전송됩니다.

**캐시 값을 줄여야 하는 이유**

Redis는 모든 데이터를 메모리에 저장합니다. 그래서 값이 커지면 여러 곳에서 동시에 비용이 늘어납니다.

- **메모리는 비싼 자원입니다.** 값이 커지면 scale-out 또는 scale-up을 고려해야 합니다. 메모리가 부족해지면 삭제(eviction)할 키를 선택해야 하고, 그 결과 캐시 적중률도 떨어질 수 있습니다.
- **네트워크 대역폭의 한계에 먼저 도달합니다.** Redis 노드가 내보내는 트래픽은 값의 크기에 조회 수를 곱한 만큼입니다. 큰 값을 여러 애플리케이션이 자주 조회하면 메모리에 여유가 있어도 트래픽이 먼저 한계에 닿습니다.
- **큰 값은 다른 명령의 처리까지 늦춥니다.** Redis는 명령을 하나의 스레드에서 순서대로 처리합니다. 큰 값을 주고받는 명령이 오래 걸리면, 뒤에서 대기 중인 작은 명령들도 함께 지연됩니다.
- **애플리케이션의 부담도 커집니다.** 조회할 때마다 바이트를 다시 객체로 변환해야 하므로, 값이 크고 조회가 잦을수록 직렬화에 드는 CPU와 메모리 부담이 커집니다.

저장 형식의 안정성도 중요합니다. 클래스의 필드나 패키지를 바꾸는 평범한 배포가 기존 캐시 값을 읽지 못하게 만들면, 캐시가 오히려 장애의 원인이 됩니다. 그래서 새로운 형식을 고를 때는 크기와 속도뿐 아니라, 클래스가 바뀌어도 기존 값을 읽을 수 있는지도 함께 살펴봤습니다.

값을 줄이는 방법은 직렬화 형식을 바꾸는 것과 바이트를 압축하는 것, 두 가지입니다. 다음 두 장에서 각각 Fory와 압축 방식을 소개합니다.

## 2\. Fory 직렬화 도구 소개

**Apache Fory는 Java 객체를 그대로 받아, JSON보다 작고 빠르게 바이트로 변환하는 직렬화 프레임워크입니다.** Ant Group에서 Fury라는 이름으로 시작해 Apache 재단에 기증되었고, 2025년에 이름을 Fory로 바꾼 뒤 Apache 최상위 프로젝트가 되었습니다. Java 외에도 Python, C++, Go, JavaScript, Rust 등 여러 언어를 지원합니다.

### Jackson과의 차이

같은 객체를 저장하더라도 바이트를 만드는 방식이 다릅니다. 주요 차이는 다음과 같습니다.

| 항목 | Jackson (JSON) | Fory |
| --- | --- | --- |
| 형태 | 텍스트 (사람이 읽을 수 있음) | 바이너리 |
| 숫자 | 문자로 저장 (`12345`는 5바이트) | 가변 길이 바이너리로 저장 (작은 수는 1~2바이트) |
| 타입 정보 | 필요하면 패키지를 포함한 클래스 이름 저장 | 등록한 짧은 번호나 이름 저장 |

1장의 메뉴 목록을 예로 들면, 메뉴가 수백 개여도 `id`, `name` 같은 필드 이름은 한 번만 저장됩니다. 구조화된 객체가 크고 반복이 많을수록 차이가 커집니다. 반대로 문자열이 대부분인 값은 문자열 자체를 줄이지 못하기 때문에 차이가 크지 않습니다.

### Fory가 빠르고 작은 이유

- **실행 중 코드 생성:** 클래스를 처음 만나면 해당 클래스 전용 직렬화 코드를 생성해 둡니다. 이후에는 리플렉션 없이 필드를 바로 읽고 씁니다.
- **효율적인 인코딩:** 정수는 값의 크기에 맞춘 가변 길이로, 문자열은 내용에 맞는 문자 인코딩으로 저장합니다.
- **메타데이터 공유:** 필드 이름 같은 타입 정보는 한 번만 저장하고, 같은 타입의 다음 객체는 이를 참조만 합니다.
- **복사 최소화:** 큰 바이트 배열 같은 데이터는 가능하면 복사하지 않고 버퍼를 그대로 전달합니다.

## 3\. 압축 방식 소개

**직렬화가 데이터의 구조를 줄인다면, 압축은 바이트 안의 반복을 줄입니다.** 같은 필드 이름과 비슷한 값이 반복되는 JSON은 압축 효과가 큰 데이터입니다. Redis 캐시에 적용할 후보로 검토한 세 가지 방식을 소개합니다.

### gzip: 가장 널리 쓰이는 표준

DEFLATE 알고리즘(LZ77 + 허프만 부호화)을 사용하는, 가장 오래되고 널리 쓰이는 형식입니다. JDK의 `java.util.zip`에 포함되어 있어 별도 라이브러리가 필요 없습니다. 압축률은 무난하지만, 세 가지 중 압축과 해제 속도가 가장 느린 편입니다.

### snappy: 압축률보다 속도

Google이 2011년에 공개한 형식으로, 압축률을 조금 포기하는 대신 처리 속도를 높이는 데 초점을 맞췄습니다. 압축 레벨은 선택할 수 없습니다. CPU 사용량은 가장 적지만, 압축 결과는 세 가지 중 가장 큽니다.

### zstd: 압축률과 속도를 함께

Zstandard(zstd)는 Facebook(현 Meta)이 2016년에 공개한 형식입니다. gzip과 비슷하거나 더 나은 압축률을 내면서도 압축과 해제가 훨씬 빠릅니다. 레벨 범위가 넓어 속도와 압축률 사이에서 원하는 지점을 고를 수 있습니다.

## 세 방식 비교

세 방식의 특징을 표로 정리하면 다음과 같습니다.

| 항목 | gzip | snappy | zstd |
| --- | --- | --- | --- |
| 압축률 | 좋음 | 낮음 | 좋음 (레벨에 따라 gzip 이상) |
| 압축, 해제 속도 | 느림 | 매우 빠름 | 빠름 |
| 레벨 | 1~9 (기본 6) | 없음 | 음수(`--fast`) ~ 22 (기본 3) |
| Java에서 사용하는 방법 | JDK 내장 | 라이브러리 (네이티브 바인딩 또는 순수 Java) | 라이브러리 (zstd-jni 또는 순수 Java 구현) |
| 식별 바이트(매직 바이트) | `1F 8B` | 기본 형식에는 없음 | `28 B5 2F FD` |

매직 바이트는 사소해 보여도 운영에서는 유용합니다. 저장된 값의 첫 바이트만 보고도 압축 여부와 형식을 구분할 수 있기 때문입니다.

압축에도 비용은 있습니다. 압축된 데이터에는 헤더가 붙고, 작은 값은 줄일 반복도 적어서 수백 바이트 이하의 작은 값은 거의 줄지 않거나 오히려 커지기도 합니다. 이를 확인하기 위해 실험 환경을 구성하고 직접 측정했습니다.

## 4\. Fory와 압축 방식 적용 실험

실제 효과를 검증하기 위해 사내 베타 환경에서 두 가지 실험을 진행했습니다. 먼저 직렬화 포맷별 성능을 비교하고, 각각의 직렬화 결과물에 압축을 적용해 비교했습니다. 비교군으로는 기존에 쓰던 JSON(Jackson)과 함께, 가장 널리 쓰이는 바이너리 직렬화 포맷인 Protocol Buffers(이하 Proto)를 넣었습니다.

측정 지표는 최종 바이트 크기와 프로세스 CPU 시간입니다. 객체를 직렬화하고 압축한 뒤, 다시 압축을 해제하고 역직렬화해 객체로 복원하기까지의 과정을 한 번의 operation으로 정의했습니다.

## 1차 실험: 직렬화 / 역직렬화만 적용한 결과

압축 없이 직렬화만 했을 때의 결과입니다. 괄호 안은 JSON 대비 비율입니다.

**바이트 크기**

| --- | --- | --- | --- |
| 객체 단건 | 243 | 190 (78%) | 155 (64%) |
| 객체 200개 List | 49,240 | 25,077 (51%) | 31,884 (65%) |

### 1차 실험 결과 해석

바이트 크기에서는 작은 객체는 Proto가, 큰 객체는 Fory가 가장 작았습니다. Fory는 호환 모드에서 클래스의 메타데이터를 함께 담기 때문에 작은 객체에서는 불리하지만, 반복되는 객체 사이에서 메타데이터를 공유하기 때문에 List 형태의 객체에서는 유리합니다.

프로세스 CPU 시간에서는 두 실험군 모두 Fory가 우수했습니다. 특히 객체 200개 List에서는 JSON 대비 바이트 크기는 51%, 프로세스 CPU 시간은 24% 수준으로 줄었습니다.

### 2차 실험 결과 해석

실험을 통해 세 가지 특징을 확인했습니다.

**① 작은 객체는 압축 효과가 거의 없습니다.**

243바이트의 작은 객체에서는 압축 효과가 미미하거나 오히려 크기가 커졌습니다.

경계를 확인하기 위해 본문에 싣지 않은 중간 크기 실험군(JSON 기준 약 0.4KB, 1.1KB, 2.1KB)의 zstd 결과도 함께 살펴봤습니다. 아래는 각 포맷에서 zstd 압축 후 크기가 압축 전의 몇 %인지 나타낸 값입니다.

| JSON 기준 크기 | JSON | Fory | Proto |
| --- | --- | --- | --- |
| 422바이트 | 84% | 98% | 96% |
| 1,147바이트 | 53% | 74% | 65% |
| 2,109바이트 | 37% | 55% | 48% |

0.4KB에서는 JSON만 조금 줄었고, Fory와 Proto는 거의 줄지 않았습니다. 1KB를 넘자 세 포맷 모두 26~47%가 줄었습니다. 그래서 JSON 직렬화 크기 1KB를 압축 적용 기준으로 삼았습니다.

**② 직렬화 포맷에 따른 크기 차이는 압축 후 줄어듭니다.**

큰 객체에서는 압축을 적용하면 각 직렬화 결과물 크기의 약 15~35%로 줄어들었습니다. 압축 전에는 JSON이 Fory의 약 2배였지만, zstd 압축 후에는 1.2배 차이로 줄었습니다.

이는 세 가지 압축 방식이 모두 LZ 계열이기 때문입니다. LZ는 알고리즘을 만든 Abraham **L** empel과 Jacob **Z** iv의 이름 첫 글자를 딴 것입니다. LZ 압축은 앞에 나온 것과 같은 문자열을 만나면 그 위치와 길이만 기록합니다. 그래서 JSON에서 반복되는 필드 이름이나 괄호, 따옴표 같은 구조적 정보는 대부분 짧은 참조로 바뀌고, 반복되지 않는 값만 남습니다. 결과적으로 어떤 직렬화 포맷을 쓰든 압축 후 크기는 비슷해집니다.

**③ 압축률과 프로세스 CPU 시간은 서로 상충합니다.**

바이트 크기는 gzip, zstd, snappy순으로 작았으며, 프로세스 CPU 시간은 그 반대였습니다. 라이브러리 기본 압축 레벨(gzip 6, zstd 3)을 기준으로 측정한 결과입니다.

이 결과는 [zstd 저장소의 README](https://github.com/meta/zstd) 에 소개된 벤치마크와 다릅니다. README 벤치마크에서는 zstd가 압축률과 속도 모두 앞서지만, 압축 레벨을 모두 1로 맞춘 결과입니다. 이번 실험은 각 라이브러리의 기본 레벨을 그대로 썼기 때문에, 더 높은 레벨에서 압축한 gzip이 조금 더 작게 압축했습니다.

## 실험 결론

실험을 통해 캐시 값의 크기를 줄이는 데에는 **압축이, 직렬화와 역직렬화의 CPU 비용을 줄이는 데에는 Fory가 효과적임** 을 확인했습니다.

다만 실험에서 가장 좋은 성능을 보인 방식이 반드시 운영 환경에서도 최선의 선택인 것은 아닙니다. 다음 장에서는 실험 결과를 바탕으로 실제 서비스에 적용할 기준을 소개합니다.

## 5\. 기준 선택과 주의사항

### 직렬화 포맷

실험 결과를 보면 직렬화 결과물의 크기와 처리 속도 측면에서 Fory가 우수하지만, Fory로 전환하는 데에는 여러 난관이 있습니다.

① 직렬화하는 서버와 역직렬화하는 서버가 같은 클래스 정보를 공유해야 합니다.
② [IANA에 등록된 표준 미디어 타입](https://www.iana.org/assignments/media-types) (`application/json` 같은)이 없어 다른 서버와의 통신에 사용하기 어렵습니다.
③ 데이터 가독성이 떨어집니다. 바이너리라 사람이 바로 읽을 수 없고, JSON처럼 누구나 바로 쓸 수 있는 공용 해석기도 없습니다.
④ 새로운 직렬화 규칙을 학습해야 합니다.

그래서 대부분의 상황에서는 기존처럼 JSON Mapper를 사용하고, **한 서비스 안에서만 주고받으면서 성능이 중요한 경우** 에만 Fory를 사용하는 규칙을 정했습니다.

### 압축 방식

압축 방식은 실험 결과를 토대로 zstd로 결정했습니다. Redis의 메모리 비용과 애플리케이션 서버의 CPU 비용을 함께 고려했을 때, zstd가 압축률과 CPU 사용량 사이에서 좋은 균형을 보였기 때문입니다. 또한 서비스별로 zstd 사전(Dictionary)을 적용하면 압축률과 속도를 더 개선할 여지도 있습니다.

직렬화 포맷 전환과 달리 압축 방식을 바꾸는 데에는 큰 난관이 없지만, 무중단 서비스에서 데이터의 포맷과 압축 방식이 바뀌는 배포를 할 때는 주의가 필요합니다.

마지막 장에서는 Fory와 zstd를 모두 채택했을 때 적용했던 전환 규칙과 체크리스트를 소개합니다.

## 6\. 적용하면서 정한 규칙과 전환 절차

Fory는 간단한 설정으로 적용할 수 있지만, 적용 후에도 지속적으로 관리해야 할 사항이 생깁니다. 기존 값이 쌓인 캐시를 옮기는 일, Redis에 넣는 타입을 빠짐없이 등록하는 일, 클래스를 고칠 때 옛 값을 깨뜨리지 않는 일입니다. 이 장에서는 관리 포인트마다 정한 규칙을 소개합니다.

### A. 공통: 기존 캐시는 듀얼 라이트로 전환합니다

**가장 중요한 점은 어느 이미지로 롤백해도 캐시 값을 읽을 수 있어야 한다는 것입니다.** 롤백은 대개 급하게, 이미지를 통째로 되돌리는 방식으로 하기 때문입니다.

그래서 새 배포본은 기존 키와 버전을 붙인 새 키에 함께 씁니다. 읽을 때는 새 키를 먼저 읽고, 값이 없으면 기존 키에서 읽습니다. 직렬화를 Fory로 바꿀 때도, JSON은 그대로 두고 zstd 압축만 붙일 때도 같은 방식이고 새 키 이름만 다릅니다(`shopSummary-fory-v1`, `shopSummary-zstd-v1`).

전환은 두 번의 배포로 나눠 진행합니다. 1차 배포에서는 두 키에 함께 쓰고, 지표가 안정되면 2차 배포에서 기존 키 쓰기를 멈춥니다. 아래 그림은 배포 단계마다 어느 키에 쓰고 어느 키에서 읽는지 보여 줍니다.

![](https://techblog.woowahan.com/wp-content/uploads/2026/11/dualwrite-flow-750x588.png)

- **쓰기와 지우기는 언제나 두 키에 합니다.** 한쪽만 지우면 다른 쪽에 남은 옛 값을 읽습니다.
- **롤백했다가 다시 배포할 때는 키 버전을 올립니다.** 롤백한 동안 새 키는 갱신되지 않아 낡은 값이 남아 있기 때문입니다.
- **기존 키 쓰기는 롤백할 수 있는 이미지가 모두 1차 배포 이후의 것이 되고, 지표가 안정된 뒤에 멈춥니다.**

TTL이 없는 키는 1차 배포 기간에 저절로 옮겨지지 않으므로, 2차 배포 전에 기존 값을 새 키로 백필합니다. `SET NX`(키가 없을 때만 저장)로만 채우고, 그 사이 기존 키가 바뀌었으면 채운 값을 되돌려 서비스의 쓰기와 경합하지 않게 합니다.

TTL이 짧은 캐시라면 새 키에만 쓰고 기존 키는 만료되게 두는 것으로 충분합니다. 듀얼 라이트는 전환 기간에 메모리를 추가로 사용하므로, 여유가 빠듯하면 캐시 묶음별로 나눠 진행합니다.

### B. 직렬화: Fory 설정은 기본값에 맡기지 않습니다

**HTTP 응답의 Jackson은 그대로 두고 Redis 값 직렬화기만 바꾸며, 아래 설정은 항상 명시합니다.** 설정 코드와 각 옵션의 의미는 다음과 같습니다.

```java
ThreadSafeFory fory = Fory.builder()
        .withLanguage(Language.JAVA)
        .requireClassRegistration(true)
        .withCompatibleMode(CompatibleMode.COMPATIBLE)
        .serializeEnumByName(true)
        .withDeserializeUnknownClass(false)   // 선택
        .buildThreadSafeFory();
```

| 옵션 | 값 | 설명 |
| --- | --- | --- |
| `withLanguage` | `JAVA` | Java(Kotlin 포함) 서비스끼리만 읽고 쓰는 형식을 씁니다 |
| `requireClassRegistration` | `true` | 등록한 타입만 읽고 씁니다. 끄면 값마다 패키지까지 포함한 클래스 이름이 실려 크기가 커지고, 패키지를 옮기는 것만으로 옛 값을 못 읽습니다. Jackson의 `@class` 타입 정보와 같은 약점입니다 |
| `withCompatibleMode` | `COMPATIBLE` | 필드를 추가하거나 지워도 옛 값을 읽습니다. 없는 필드는 기본값으로 채우고, 지워진 필드는 무시합니다 |
| `serializeEnumByName` | `true` | enum을 순서 번호가 아니라 이름으로 저장합니다. 기본값인 순서 번호로 저장하면 상수 순서만 바꿔도 예외 없이 다른 값으로 읽힙니다 |
| `withDeserializeUnknownClass` | `false` (선택) | 모르는 타입을 빈 구조체로 읽지 않고 읽는 단계에서 거부합니다. 꺼내 쓰는 코드에서 `ClassCastException`이 나는 대신 캐시 미스로 처리됩니다 |
| `buildThreadSafeFory` |  | 스레드에 안전한 인스턴스를 하나 만들어 공유합니다. 만드는 비용이 크고, 생성해 둔 직렬화 코드를 계속 재사용하기 위해서입니다 |

### C. 직렬화: 클래스 등록과 변경은 규칙으로 막습니다

**등록 이름은 클래스에 애노테이션으로 달고, 기동할 때 스캔해서 등록합니다.** 번호로 등록하면 다음 번호를 누군가 관리해야 하고, 등록 목록을 한 곳에 모으면 클래스를 추가할 때 빠뜨리기 쉽습니다. Fory는 이런 애노테이션을 제공하지 않아 직접 만들었습니다. 사용하는 모습은 아래와 같습니다.

```java
@RedisValueType("shop-summary")                       // 등록 이름. 바꾸지도, 재사용하지도 않는다
public class ShopSummaryCache implements RedisValue { ... }

public interface RedisValue {}                         // Redis에 저장하는 타입이라는 표시

public <T extends RedisValue> void set(String key, T value) { ... }   // 표시 없는 타입은 컴파일 실패
```
- **이름이 겹치거나 애노테이션이 빠지면 기동을 거부합니다.** 등록이 빠지면 운영에서 그 값을 처음 저장할 때에야 오류가 발생하고, 중첩 DTO는 해당 필드에 값이 할당될 때 비로소 오류가 발생하기 때문입니다.
- **`RedisValue` 인터페이스로 컴파일 단계에서 검증합니다.** 컴파일러는 애노테이션이 아니라 타입을 검사하므로, 저장 메서드를 `RedisValue`만 받게 합니다.
- **ArchUnit 테스트로 테스트 단계에서 잡습니다.** `RedisValue` 구현체에 애노테이션이 빠졌는지, 그 안의 중첩 DTO와 enum에도 달렸는지, `@Cacheable` 반환 타입이 `RedisValue`인지를 규칙으로 검사합니다. `@Cacheable`은 반환값을 `Object`로 캐시에 넣어 컴파일 검사가 걸리지 않기 때문입니다. 저장 타입마다 샘플을 한 번씩 직렬화한 뒤 읽는 왕복 테스트도 함께 둡니다. 애노테이션 누락을 검사하는 규칙은 아래와 같습니다.
```java
@ArchTest
static final ArchRule redisValueHasName =
        classes().that().implement(RedisValue.class)
                 .should().beAnnotatedWith(RedisValueType.class);   // 애노테이션이 빠지면 테스트 실패
```
- **필드와 enum 상수는 이름을 바꾸지 않습니다.** 호환 모드는 이름으로 맞추기 때문에, 이름을 바꾸면 예외 없이 기본값으로 읽혀 오류 지표에도 잡히지 않습니다. 꼭 바꿔야 하면 키 버전을 올립니다. enum 상수를 추가할 때는 모든 인스턴스를 배포한 뒤에 그 값을 쓰기 시작합니다.

운영에서는 트래픽을 받기 전에 등록된 타입을 한 번씩 직렬화·역직렬화하여 워밍업하고, 직렬화와 역직렬화 실패 횟수를 지표로 수집합니다.

### D. 압축: 키 묶음 단위로 켜고, 첫 바이트로 구분합니다

**압축은 값마다 크기를 보고 정하지 않고, 키 묶음(캐시 이름, key prefix) 단위로 켭니다.** 같은 타입의 값이 압축된 상태와 압축되지 않은 상태로 섞여 있으면 운영 중 문제의 원인을 추적하기 어렵기 때문입니다. 기준은 4장의 결과대로 그 묶음의 평균 값 크기가 1KB 이상인지입니다. 그보다 작은 값은 압축해도 거의 줄지 않거나 오히려 커집니다.

- **압축 여부는 값의 첫 바이트로 구분합니다.** 3장에서 본 매직 바이트(zstd는 `28 B5 2F FD`) 덕분에, 압축을 켜거나 꺼도 읽기 경로 하나로 옛 값과 새 값을 모두 읽습니다.
- **이미 gzip을 쓰던 캐시는 `1F 8B`로 구분해 그대로 읽습니다.** 압축된 값과 그렇지 않은 값이 섞여 있어도 읽기가 깨지지 않습니다.
- **압축을 켜는 것도 포맷 변경입니다.** 압축을 풀 줄 모르는 이전 이미지가 읽지 못하므로, A의 듀얼 라이트로 새 키(`-zstd-v1`)에 씁니다.

압축을 켤 때의 전환 순서는 A와 같고, 아래 그림에서 달라지는 것은 새 키 이름(`-zstd-v1`)과 읽을 때 첫 바이트로 압축 여부를 판별하는 단계뿐입니다.

### E. 서비스마다 다른 판단은 체크리스트로 합니다

**판정은 프로젝트가 아니라 키 묶음(캐시 이름, key prefix) 단위로 합니다.** 한 프로젝트 안에서도 묶음마다 serializer와 TTL, 값 크기가 다르기 때문입니다. 항목마다 문제가 없는지(), 대응이 필요한지(), 전환하면 안 되는지()를 근거와 함께 판정합니다. 확인할 항목은 다음과 같습니다.

| 구분 | 영역 | 확인할 것 |
| --- | --- | --- |
| 공통 | 기존 데이터 호환 | 배포 중이나 롤백 뒤에도 서로의 값을 읽는가, 다른 서비스가 같은 키를 읽는가 |
| 직렬화 | 스키마 진화 | 호환 모드, enum 저장 방식, 등록 이름, 필드·상수 이름 변경 |
| 직렬화 | 타입 호환 | null 캐싱, 다형성 필드, Kotlin, JPA 엔티티, Jackson 애노테이션 |
| 압축 | 압축 대상 | 키 묶음의 평균 값 크기가 1KB 이상인가 |
| 압축 | 형식 판별 | 기존 값에 이미 압축된 값이 섞여 있는가, 첫 바이트로 구분되는가 |

### F. 규칙과 체크리스트는 스킬로 묶었습니다

듀얼 라이트 래퍼, 백필, 등록 애노테이션은 Fory가 제공하지 않아 서비스마다 직접 만들어야 하고, 체크리스트도 코드를 직접 살펴보고 하나씩 판단해야 합니다. 그래서 이 내용을 AI 스킬로 묶어 사내에 공유했습니다. 프로젝트에서 실행하면 체크리스트를 판정한 리포트를 만들고, 원하면 이 장의 코드까지 만들어 빌드로 확인합니다.

## 마치며

실험 결과를 바탕으로 운영 중인 두 서비스의 Redis에 zstd 압축을 적용했습니다. 적용 전후 수치는 다음과 같습니다.

| 구분 | 서비스#1 | 서비스#2 |
| --- | --- | --- |
| 저장하는 데이터 | 큰 집계 데이터를 담는 조회용 캐시 | 사용자 행동 로그를 담는 세션 저장소 |
| Redis 메모리 | 352.9GB → 297.7GB (**84.4%**) | 216.3GB → 67.9GB (**31.4%**) |
| Redis 아웃바운드 | 239.8TB/일 → 115.7TB/일 (**48.2%**) | – |
| 값 하나의 평균 크기 | 124.5KB → 57.7KB (**46.3%**) | 1,367바이트 → 388바이트 (**28.4%**) |

데이터는 그대로 두고 적절한 기술을 골라 시스템 비용을 낮춘, 서버 엔지니어로서 보람찬 작업이었습니다. 이 적용기가 비슷한 고민을 하는 개발자에게 도움이 되기를 바랍니다.
