# 모듈은 깊어야 한다

## 모듈화 설계

모듈화 설계에서는 소프트웨어 시스템을 여러 개의 *모듈*로 분해한다.

모듈은 서로의 함수나 메서드를 호출하며 함께 동작해야 한다. 따라서 모듈 사이에는 *의존성*이 생긴다.

의존성을 식별하고 관리하기 위해 각 모듈을 *인터페이스*와 *구현*이라는 두 부분으로 나누어 생각한다.

가장 좋은 모듈은 인터페이스가 구현보다 훨씬 단순한 모듈이다.
- 단순한 인터페이스는 모듈이 나머지 시스템에 지우는 복잡성을 최소화한다.
- 인터페이스를 건드리지 않고 모듈을 수정하면 다른 모듈은 아무 영향도 받지 않는다.

## 깊은 모듈

가장 좋은 모듈은 강력한 기능을 제공하면서도 인터페이스는 단순하다.

![[deep-vs-shallow-module.png]]

모듈의 깊이는 비용 대비 이득을 따져 보는 사고방식이다. 모듈이 주는 이득은 기능이고, 비용은 인터페이스다.

Unix와 그 계보를 잇는 운영체제가 제공하는 파일 I/O 메커니즘은 깊은 인터페이스의 아름다운 예다. I/O용 기본 시스템 콜은 다섯 개뿐이다.
```c
int open(const char* path, int flags, mode_t permissions);
ssize_t read(int fd, void* buffer, size_t count);
ssize_t write(int fd, const void* buffer, size_t count);
off_t lseek(int fd, off_t offset, int referencePosition);
int close(int fd);
```

요즘의 Unix I/O 구현은 코드가 수십만 줄에 이르며, 다음과 같은 복잡한 문제를 다룬다.
- 효율적인 접근이 가능하도록 파일을 디스크에 어떻게 표현할 것인가?
- 디렉터리는 어떻게 저장하며, 계층적인 경로 이름을 어떻게 해석해서 해당 파일을 찾을 것인가?
- 한 사용자가 다른 사용자의 파일을 수정하거나 삭제하지 못하도록 권한을 어떻게 강제할 것인가?
- 파일 접근은 어떻게 구현할 것인가? 예를 들어 인터럽트 핸들러와 백그라운드 코드 사이에 기능을 어떻게 나누고, 이 둘은 어떻게 안전하게 통신할 것인가?
- 여러 파일에 동시에 접근할 때 어떤 스케줄링 정책을 쓸 것인가?
- 디스크 접근 횟수를 줄이기 위해 최근에 접근한 파일 데이터를 메모리에 어떻게 캐싱할 것인가?
- 디스크, 플래시 드라이브 같은 다양한 보조 저장 장치를 어떻게 하나의 파일 시스템으로 통합할 것인가?

## 얕은 모듈

> [!WARNING]
> 얕은 모듈은 제공하는 기능에 비해 인터페이스가 복잡한 모듈이다. 이런 모듈은 복잡성과 싸우는 데 별 도움이 안 된다. 내부 동작을 몰라도 된다는 이득이 인터페이스를 익히고 쓰는 비용에 묻히기 때문이다. 작은 모듈은 얕기 쉽다.

### 클래스염(Classitis)

프로그래밍의 통념에 따르면 클래스는 깊어야 하는 게 아니라 작아야 한다. "클래스는 작아야 한다"는 접근을 극단까지 밀어붙인 증후군을 나는 클래스염(classitis)이라 부른다. "클래스는 좋은 것이니 클래스가 많을수록 더 좋다"는 착각에서 비롯된 병이다.

#### 예시: Java와 Unix I/O

예를 들어 Java 개발자는 파일을 열고 직렬화된 객체를 읽으려면 서로 다른 객체를 세 개나 만들어야 했다.
```java
FileInputStream fileStream = new FileInputStream(fileName);
BufferedInputStream bufferedStream = new BufferedInputStream(fileStream);
ObjectInputStream objectStream = new ObjectInputStream(bufferedStream);
```

`FileInputStream` 객체는 아주 기초적인 I/O만 제공한다. 버퍼링도 안 되고, 직렬화된 객체를 읽고 쓰지도 못한다. `BufferedInputStream` 객체는 `FileInputStream`에 버퍼링을 더하고, `ObjectInputStream`은 직렬화된 객체를 읽고 쓰는 기능을 더한다. 파일을 열고 나면 앞의 두 객체 `fileStream`과 `bufferedStream`은 다시 쓸 일이 없다. 이후 작업은 전부 `objectStream`으로 한다.

인터페이스는 흔한 경우가 가장 단순해지도록 설계해야 한다. 파일 I/O를 쓰는 사람은 거의 다 버퍼링을 원하므로 버퍼링은 기본으로 제공해야 한다.

## 결론

모듈의 인터페이스를 구현과 분리하면 구현의 복잡성을 나머지 시스템에서 감출 수 있다. 모듈을 쓰는 쪽은 인터페이스가 제공하는 추상화만 이해하면 된다. 클래스를 비롯한 모듈을 설계할 때 가장 중요한 문제는 모듈을 깊게 만드는 것이다. 흔한 사용 사례에는 단순한 인터페이스를 내주면서도 기능은 충분히 갖추게 하라는 뜻이다. 그래야 가장 많은 복잡성을 감출 수 있다.
