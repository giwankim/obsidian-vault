# WIL - 1주차 (모호한 쿠폰 요구를 구현 가능한 설계로 바꾸기)

## 🧠 이번 주에 새로 배운 것

- 경험상 모호한 요구 사항을 개발자 자의로 해석하고 구현하다 보면 나중에 힘들어진다는 사실은 알고 있었으나,
	- 구체적으로 불변식과 제약 조건을 발견하고
	- 이를 반례로 다듬는다는 것을 배웠다.
- 깊은 모듈(= 인터페이스 + 구현)을 지향하는 이유
	- John Ousterhout 교수님의 [A Philosophy of Software Design](https://web.stanford.edu/~ouster/cgi-bin/book.php)에서 이 주제에 대해 쓰신 부분을 읽어 보았다. 이를 Writing Quest 주제로 삼았다. 참고로 이분은 Stanford 교수님이셨고 분산 시스템의 Raft 알고리즘과 Tcl 언어를 만드셨으며, 자바를 만든 팀은 아니지만 Sun Microsystems에서 일하셨던 분이라 CS의 전설적인 인물이다. 이 책에는 클린 코드를 반박하는 내용도 있어서 최근에 [로버트 마틴](https://github.com/johnousterhout/aposd-vs-clean-code/blob/main/README.md)과 열띤 토론도 하셨다고 한다.

## 💭 이런 고민이 있었어요

- 주로 쿠폰보다는 dynamic pricing을 사용하는 이커머스 플랫폼을 다뤄 봤기에 발제문에 나와 있는 불변식과 제약 조건을 인용했다.
- 아직 무엇을 구현하려 하는지에 대한 컨텍스트가 부족해서 그런지 과제보다는 다양한 쿠폰 정책 인터페이스, strategy 디자인 패턴, 추상 클래스 같은 구현적인 것들부터 떠올라서 당황했다.
- 일반적으로 유저 스토리가 시발점이라 생각하는데 불변식이라는 조금 생소한 용어와 이를 어떻게 문서화할지에 대해 고민했다.
	- 전에 ATDD를 조금 공부한 적이 있는데 과제에서 요구한 classification test보다 더 자연스러운 전개일 수도 있다는 생각이 든다.
- 이번 과제에서 작성한 E2E 테스트에서 검증해야 할 것을 테스트 피라미드 기반으로 생각해 봤을 때, MVC 슬라이스 테스트가 추가되면 예외 케이스는 그곳으로 옮기고 BDD 스타일의 happy path만 E2E로 `DispatcherServlet`을 띄우고 `Rest(Test)Client`로 테스트할 것 같다.

## 💡 앞으로 실무에 써먹을 수 있을 것 같은 포인트

- 기획자의 모호한 요구 사항에 대해 sync를 맞추는 작업에서 추출할 정보가 구체적으로 무엇인지 알게 되었다. 테스트 케이스를 엑셀에 적어서 공유하는 것을 보았는데 불변식과 제약 조건이 더 본질에 가까운 것 같다.
- 시스템 디자인 면접을 공부하면서 프로젝트 초기에 갖추어야 할 디자인 문서 템플릿을 알게 되었는데, 역시 멘토님들도 같은 이야기를 하셔서 확신이 생겼다.

## 🤔 아쉬웠던 점 & 다음 주에 해보고 싶은 것

- 금주에는 컨디션 난조로 원하는 만큼 학습하지 못했다.
- 예전에 조영호 님의 DDD 강의에서 도메인 모델링 시 불변식 발견의 중요성에 대해 들었기에, 에릭 에반스나 반 버논이 이에 대해 쓴 글을 읽어 보고 싶었는데 건강상의 이유로 충분히 보지 못해서 아쉽다.
- 발견한 불변식과 제약 조건을 어떻게 도메인 구현에 녹여낼지 기대된다.
